## 3. Fixed selection rules, as implemented

- Target: 2,500 healthcare + 2,500 real_estate = 5,000 — a **balanced sample within these two eligible sectors**, not a claim about their actual proportion of the source corpus or the wider economy (see §1.3/§1.4).
- Healthcare = source `industry` exactly (case/whitespace-normalized) `hospital & health care` or `medical practice`. Real estate = exactly `real estate`.
- These three strings, and no others, were chosen after an actual full-corpus scan for every industry value containing "health", "medical", "hospital", "clinic", "real estate", "realty", or "property". That scan found 8 distinct values; 5 were deliberately excluded (`commercial real estate`, `health, wellness and fitness`, `hospitality`, `medical devices`, `mental health care`) because they are adjacent but not the two categories the brief specified. `hospitality` would have been a false positive under substring matching (it starts with "hospital") — exactly the bug class flagged in `docs/upgrade/audit.md` B.3, avoided here by exact matching only.
- Country = source `country` exactly `united states` (a full-corpus scan of all 249 distinct country values found no abbreviation/alias variant actually present in this file).
- No company-size floor. Website optional, missing preserved as `null`, never fabricated. Raw source values preserved in full per row.
- Segment membership is stored and labeled explicitly as a **candidate classification** (`cleaned_data.segment_is_candidate_classification_only: true` on every imported Lead) — never as a qualification, buying-intent, or operational-pain claim.

No shortfall occurred in either segment, so the shortfall-reporting path was not exercised on the real data — it *was* exercised on a synthetic fixture, deliberately (`test_pdl_curation_fixtures.py::test_honest_shortfall_when_insufficient_eligible_records`), specifically because the real run couldn't demonstrate it.

## 4. What was built (Part C: the CLI)

One entry point, `backend/app/pdl/cli.py`, five subcommands, run as `python -m app.pdl.cli <subcommand>` from `backend/` with `PYTHONPATH=.`:

```
download   --cache-dir DIR
inspect    --cache-dir DIR --limit N
curate     --cache-dir DIR --output-dir DIR --seed N --limit N [--source-checksum SHA] --dry-run
import     --manifest PATH --seed N --dry-run
report     --output-dir DIR
```

`--source-checksum` on `curate` is now an **optional cross-check assertion only** (Phase 3 closeout, Part B.1) — the real checksum is always derived by re-hashing the actual cached/downloaded file via `download_source()`, never trusted solely from a flag a human might forget to pass. See §5 for exactly why this changed.

Supporting modules under `backend/app/pdl/`:

- `config.py` — target counts, the versioned industry/country alias maps, provider/mirror/checksum constants, Part E defaults (CSV byte/row caps, pagination page size).
- `download.py` — resumable, checksummed, disk-space-checked streaming download to a `.part` file, renamed only on verified completion. **Closeout addition**: a `<file>.meta.json` sidecar recording the real `downloaded_at` (see §2).
- `source_reader.py` — streaming gzip + JSONL parsing, bounded per-row size, bounded stored error examples (unbounded counts), a distinct `SourceCorruptError` for a truncated/corrupt gzip stream.
- `normalize.py` — field mapping, eligibility checks, never fabricates a value.
- `identity.py` — the (source_id | fingerprint) identity key and a normalized-content hash.
- `identity_store.py` (**new in the Phase 3 closeout**, Part C.1) — a disk-backed (temp SQLite file), LRU-cached identity/content-hash index, replacing the original in-memory `dict`. See §6.
- `curate.py` — streaming eligibility filter, dedup/conflict detection (now via `identity_store.py`), seeded per-segment reservoir sampling.
- `importer.py` — chunked (500 rows/chunk), individually-committed, idempotent DB writes. **Closeout fixes**: mandatory (not optional) checksum before any write; race-safe find-or-create for both `SourceSnapshot` and `LeadBatch`, catching the database's own unique-constraint violation and re-reading the winning row instead of raising or duplicating; `LeadBatch` matched by a persisted `logical_key` column, not a name-prefix.
- `report.py` — canonical CSV, formula-injection-escaped spreadsheet-safe CSV, full-fidelity JSON manifest (now including `downloaded_at`/`curated_at`), machine-readable quality report, human-readable Markdown report.

## 5. Part B/D closeout: mandatory provenance and idempotency under concurrency

**The original handoff's Part D section said this was "verified" — that verification was real but incomplete: it never checked whether the *code*, not just remembering a CLI flag, prevented the failure it had already hit once.** The Phase 3 closeout re-inspected this specifically and found the code did **not** prevent it:

- `find_or_create_source_snapshot`'s reuse lookup was gated on `if checksum:` — when `checksum` was `None` (i.e. nobody passed `--source-checksum`), the guard was simply skipped and a **new** `SourceSnapshot` was created on every single invocation, silently, with no error. This was the actual root cause of the "duplicate snapshot" incident during the original Phase 3 work, and it was never fixed at the code level at the time — only avoided afterward by remembering to pass the flag.
- **Fixed**: `curate` now derives the checksum automatically by re-hashing the actual cached/downloaded file via `download_source()` every time it runs — the flag can no longer be "forgotten" because it's no longer the source of truth. `import` calls a new `validate_snapshot_info()` before any write (`SourceSnapshot`, `LeadBatch`, `CompanyIdentity`, or `Lead`) and raises a precise `ProvenanceError` if the manifest's checksum/provider/mirror_url/checksum_algorithm are missing, empty, or malformed — verified with 8 focused tests (`test_pdl_identity_idempotency.py`) covering each missing/empty/malformed field individually.
- **A second, independent gap**: even with a correct checksum, the *application-level* SELECT-then-INSERT find-or-create pattern has a textbook TOCTOU race under concurrent writes — nothing at the database level stopped two simultaneous import attempts from both finding "nothing exists yet" and both inserting. There was no unique constraint on `SourceSnapshot(provider, checksum)` or on any persisted batch-identity column at all (the old code matched batches by a **name prefix** — the first 12 characters of the logical key, embedded in a human-editable `LeadBatch.name` — which is not an identity mechanism and could not have prevented a race even in principle, and would have broken silently if the batch were ever renamed).
- **Fixed**: new Alembic migration `0004_logical_key` (additive, does not touch 0001–0003) adds `UNIQUE(logical_key)` on `lead_batches` and `UNIQUE(provider, checksum)` on `source_snapshots`, replaces the name-prefix batch lookup with the persisted, full `logical_key` column, and **backfills** the real database's one existing PDL batch's `logical_key` from its own leads' actual provenance (their shared `source_snapshot_id` and the `ImportRun.config_seed` that produced them) — the migration aborts with a precise error naming the batch if that mapping is ever ambiguous (more than one distinct snapshot or config among a batch's leads); it never guesses from the batch's name. The real backfill was unambiguous: the resulting `logical_key` (`ac1d97f5f07be718b207fdf9bc2ce941`) matches exactly what `compute_logical_key()` independently computes from the same inputs.
- `find_or_create_source_snapshot` and `find_or_create_batch` now catch the database's `IntegrityError` on a race and re-read the winning row, rather than raising or silently duplicating.
- **Verified, in this order**:
  1. Migration `0004` applied cleanly (exit 0) to a **disposable restored copy** of the real database (see §7 for the backup/restore procedure) before ever touching the real one; the backfilled `logical_key` matched the independently-computed expected value exactly; idempotent re-upgrade and a downgrade→re-upgrade round-trip both left the batch with the same correct key.
  2. 15 deterministic unit tests (`test_pdl_identity_idempotency.py`) covering: complete-provenance acceptance, each individually-missing/empty/malformed provenance field rejected before any write, convergence on identical checksum/logical_key, a **renamed batch's `logical_key` match is unaffected by the rename** (proving name is no longer part of the identity mechanism), and distinct checksums/keys correctly creating distinct rows.
  3. **A real concurrent-writes test against disposable Postgres** (not SQLite, which can't represent genuine concurrent connections faithfully): 8 separate OS processes, synchronized with a `multiprocessing.Barrier` to start as close to simultaneously as possible, all racing to create a `SourceSnapshot` and `LeadBatch` for the *same* checksum/logical_key. Result: exactly 1 distinct snapshot id and 1 distinct batch id across all 8 workers; exactly 1 worker correctly reported `created=True` for each, the other 7 correctly reported `created=False` (i.e. they hit the race, caught the `IntegrityError`, and correctly read back the winner's row). This is real evidence against real concurrent database connections, not a simulation.
  4. Migration `0004` applied to the **real** persistent database (exit 0); the real batch's backfilled `logical_key` matched the expected value exactly; all 5,000 leads confirmed still present afterward.
  5. The real manifest was **re-imported against the fully corrected code** (mandatory checksum derivation + `logical_key` matching): `source_snapshot_id` and `batch_id` both reused (matching the pre-migration UUIDs exactly), `inserted=0, reused=5000, failed=0`, exit code 0. See §7 for final counts.
- **Conflict-detection code path**: the real PDL run produced zero identity conflicts (source data was clean), so this branch has no real-data example. It **is** now covered by a synthetic fixture (`test_pdl_curation_fixtures.py::test_dedup_and_conflict_and_fingerprint_and_shared_domain`) — a hand-built 15-record corpus with a deliberate same-id-different-content conflict, asserting the conflict is logged, counted, and that the *original* (first-seen) content is what's kept, not the later conflicting version. This resolves the original handoff's internal inconsistency about whether this path was ever fixture-tested: it was not, until the closeout; it now is, with the evidence cited above rather than asserted.

## 6. Part C closeout: bounded processing, and Part E closeout: bounded web uploads

**Part C.1 (disk-backed dedup index).** The original curation dedup index (`seen_identity_hash`) was a plain Python `dict`, holding one entry per *eligible* record seen (~962,000 on the real scan, not the full 32.3M-row corpus, but still unbounded in the general case). Replaced with `IdentityHashStore` (`identity_store.py`): a temp SQLite file with a bounded (50,000-entry) in-memory LRU cache in front. The reservoirs themselves were already fixed-size and are unaffected.

- **Equivalence proof, not just "it should still work"**: `test_pdl_curation_fixtures.py::test_disk_backed_identity_store_matches_plain_dict_reference` runs the *same* fixture through both the new disk-backed `curate()` and a hand-written plain-dict reference implementation of the identical eligibility/identity/first-seen-wins logic, and asserts byte-identical selected-name lists. A separate test (`test_repeated_curate_calls_are_deterministic`) confirms two `curate()` calls with the same seed+fixture select the identical rows in the identical order.
- **Not re-run against the real 32.3M-row corpus** — the closeout was explicitly told not to repeat the full corpus scan without a concrete finding requiring it, and the equivalence proof above is exactly the kind of finding-free confirmation that didn't need it. The real selection (§1) was produced by the pre-closeout in-memory-dict implementation; nothing about switching to the disk-backed store changes what that selection *would* have been, per the equivalence proof.
- Peak memory was measured on a **bounded, explicitly non-representative 3,000,000-line diagnostic run** (9.3% of the real corpus, `reached_eof: false`), not the full scan: **52.4 MiB peak RSS**, 82.7 seconds elapsed, 89,091 eligible-unique records tracked in the disk-backed index by that point. This is stated as a bounded-sample measurement, not a benchmark of the full run — extrapolating elapsed time linearly (82.7s × 32.33M/3M ≈ 891s ≈ 14.85 min) lines up closely with the real full run's actual observed wall-clock time (14m24s = 864s, from the original curate log), which is a reasonable consistency check but still an extrapolation, not a second real measurement of the full run.

**Part C.3/C.4/E (CSV upload streaming, chunked writes, partial-import recovery).** The original closeout of Phase 3's Part E left the browser CSV-upload path only partially compliant: it enforced the 20 MiB/50,000-row caps while reading, but still joined all read chunks into one in-memory `bytes` object and still wrote/committed every valid row in a single transaction — bounded by size, but not actually streaming-parse-plus-bounded-writes. This closeout finished it:

- `app/services/csv_ingestion.py` gained `iter_cleaned_leads`, a true streaming generator reading directly from a file object (never materializing the whole file or the whole row list); `parse_csv` is now a thin wrapper over it, unchanged in signature/behavior (13 existing tests pass unmodified).
- `POST /api/batches/upload` now streams the upload directly to a temp file on disk (still enforcing the 20 MiB cap while writing), then drives `iter_cleaned_leads` against that file, inserting and committing in chunks of 500 rows.
- **Partial-import semantics**: if the row-count cap is hit mid-stream, whatever was already parsed and committed (across however many whole chunks, plus whatever had been buffered in the current partial chunk) is flushed and kept — never silently discarded, never silently reported as if the whole file succeeded. The response is `422` naming exactly how many rows committed; the `LeadBatch.status` is set to `"partial"`.
- **A partial batch is excluded from Slack routing at every entry point, not overridable by `force=true`**: both `POST /api/leads/{id}/push` and `POST /api/batches/{id}/push-hot` now reject a lead/batch whose batch is `"partial"`. Verified with a transport spy (raises `AssertionError` if `httpx.post` is ever called) proving no send is attempted, for both entry points, with `force=true` (`test_partial_import_recovery.py`, 3 tests).
- **A real, independent bug was found and fixed while adding this guard**: `POST /api/batches/{id}/score` unconditionally set `batch.status = "scored"`, which would have silently overwritten `"partial"` back to a status the push guard doesn't check for — the same status-overwrite bug class Phase 2 already fixed for `Lead.status`, here recurring at the `LeadBatch` level. Fixed in `app/api/scoring.py`'s `score_one_batch`.
- **Interruption-after-a-committed-chunk, then retry**: `test_partial_import_recovery.py::test_pdl_import_chunk_failure_preserves_earlier_commits_and_retry_is_idempotent` simulates a session factory that fails on exactly its 2nd call (mid-run, between two successful chunks), confirms the chunk before the failure stayed committed and the chunk after it (a 3rd, independent chunk) also succeeded and committed, confirms the failure is reported accurately (`ChunkResult.committed=False`, a real error message, not swallowed), and confirms re-running the same import afterward with a working session factory reuses every already-committed row (no duplicates) and only inserts what was actually missing.
- **Reimport preserves existing workflow state**: `test_reimport_preserves_workflow_state.py` builds a lead via the importer, manually attaches a blocked status, an `AIOutput`, and an `AIOutputReview` to it (simulating real accumulated workflow state), re-runs the importer against the same companies, and confirms the lead's status, its output, and its review are all byte-identical (same row ids) afterward — the reimport touched nothing about it, only correctly recognized it as already-imported.

**Part E (pagination) — unchanged from the original handoff, still accurate**: all four list endpoints paginated, `total` server-computed, 200-row page cap, unique tie-breaker ordering. **What changed in the closeout**: the lead-detail page's AI-output and push-history panels, which the original handoff left as a single `limit=200` fetch with every error silently swallowed into an empty page (masking the difference between "no history" and "the request failed"). Replaced with a `usePaginatedHistory` hook (`frontend/src/hooks/usePaginatedHistory.ts`) giving each panel independent loading/error/total state, a "load more" control, a retry button on failure that **never clears already-loaded items**, and a generation counter that discards a late-arriving response for a lead the user has already navigated away from (preventing a stale-lead race). The "current outreach draft" used by approve/reject is now resolved via the existing `GET /api/leads/{id}/latest-ai-output?output_type=outreach_email` endpoint (added a thin `getLatestAIOutput` wrapper) instead of being inferred from whatever page of mixed-type history happened to be loaded — this matters architecturally even though the specific seeded-data test below didn't expose a divergence, because a lead with many `company_summary` outputs generated after its last real outreach draft could otherwise push that draft beyond a 200-row mixed-type window even though it's genuinely still "the latest outreach."
  - **Verified**: `npm run typecheck` and `npm run build` both pass clean (unchanged claim, still true, still not sufficient alone per the brief's own framing).
  - **Verified beyond 200 entries**: a disposable SQLite database was seeded with one lead carrying 250 `AIOutput` rows; walking `GET /api/leads/{id}/ai-outputs` with `limit=50` across 5 pages retrieved all 250 with `has_more` correctly transitioning to `false` on the last page — the exact request shape the frontend hook issues.
  - **Verified the authoritative-lookup endpoint**: against the same 250-output lead, `GET .../latest-ai-output?output_type=outreach_email` correctly returned the newest one (`Draft 249`) regardless of pagination state.
  - **Not verified this session**: live browser interaction (clicking "Load more," triggering and recovering from a forced network error, confirming the stale-lead race guard at runtime). Claude in Chrome was not connected in this session (a tool-availability constraint, not a choice), and no other browser-automation or component-testing framework exists in this repository (confirmed in Phase 1's audit — a deliberate scope decision then, now a real gap for this specific verification requirement). The hook's logic was carefully code-reviewed (the "preserve items on error" and "discard stale-generation responses" behaviors are directly visible in `usePaginatedHistory.ts`'s control flow, not just asserted), and the underlying API contract it depends on was verified for real as above, but this falls short of an actual recorded interaction and is stated here as an unresolved verification gap, not glossed over.
